# workflow
- For achievement/progress systems: prefer a dedicated database table to persist which achievements a player has earned, rather than re-checking conditions at runtime. This avoids repeated lookups and gives a durable per-player state. Confidence: 0.85
- For achievement thresholds: a player should earn an achievement when they beat the threshold time, even if that run is not a new personal best. Achievement is based on the threshold, not PB status. Confidence: 0.80
- For hologram backends: only use solutions compatible with Folia — HolographicDisplays is NOT Folia-compatible and should not be used. Confidence: 0.70
- When troubleshooting or researching, perform the search/research yourself instead of asking the user to run search commands. Confidence: 0.75
- Avoid asking the user to re-run processes from scratch after each debugging iteration — prefer incremental fixes. Confidence: 0.85
- For hologram leaderboard positions: Java and Bedrock locations must be independent — setting one type must NOT move the other. Users expect to position each type separately. Confidence: 0.65
- Initialization ordering for tagged resources: when a startup sequence both removes "orphan" resources (matched by a shared tag/marker) and loads fresh resources (that also carry that tag), the removal MUST run BEFORE the load. Running cleanup after loading causes freshly-loaded resources to be immediately deleted — the root cause of holograms vanishing on server restart. Generalizes to any init sequence where a "remove stale X" step and a "load fresh X" step share identifying criteria. Confidence: 0.80
- For entity-based visualization (ghosts, trajectories, replay markers): prefer a single moving entity that traverses the path rather than spawning multiple static entities at each position. A single entity is more efficient and avoids visual clutter. Confidence: 0.85
- For Folia-safe entity management: shared entity references (e.g. an ArmorStand used across region threads) must be `volatile` and protected by a removal flag (e.g. `standRemoved`) so that stale region-thread tasks can't create duplicate entities or operate on nulled fields. Always null-check before teleporting/spawning. Confidence: 0.85
- Before reporting build success (especially JAR generation), verify the actual artifact exists on the filesystem (e.g. check `build/libs` or `target/`) and confirm its timestamp, rather than relying solely on build tool output. For Minecraft plugins, also validate JAR contents (e.g. confirm `plugin.yml` is inside via `jar tf`). Confidence: 0.90
- For server-triggered client visualizations: prefer the server to automatically push relevant data to connected clients (that have the mod installed) via custom payloads when the triggering event occurs, so the client can render without requiring a separate client-side command. Confidence: 0.70
- Git remotes are hosted on GitHub; pushes require a Personal Access Token (HTTP credentials) since no SSH key or saved credential was configured in this environment. Confidence: 0.75
- When staging changes for commit, stage selectively (tracked modifications plus project source files rather than `git add .`) to avoid committing unrelated non-project files such as datasets, ML artifacts, or standalone scripts. Confidence: 0.65
- When a follow-up fix belongs with an already-written but unpushed commit, fold it in via `git commit --amend --no-edit` instead of making a separate follow-up commit, to keep related changes grouped cohesively in history. Confidence: 0.75
- Commits experimental/version-migration changes directly to `master` rather than using feature branches, even when the work is exploratory (e.g. explicitly chose "master direto" over a new branch for the Folia 26.2 migration). Confidence: 0.80
- When the user rejects or abandons a feature/idea ("remova isso", "n vou levar essa ideia pra frente"), remove it completely: delete the source files, remove all references and call sites, and rebuild to verify — do not leave commented-out or disabled dead code around. Confidence: 0.85
- Builds Java projects (Minecraft/Bukkit plugins) with Maven (`mvn -B package`), targeting Java 21; expects shaded JARs (maven-shade-plugin) as build output with `plugin.yml` included. When Maven isn't installed and isn't in winget, download the official Maven binary zip and extract it, setting `JAVA_HOME`/`MAVEN_HOME`/PATH in a build wrapper script. Confidence: 0.70
- When Maven dependencies are already cached in `.m2` (e.g. after a first build in the environment), run builds in offline mode (`mvn -B -o compile` / `mvn -B -o package`) to skip network resolution and speed up compile/package cycles. Confidence: 0.70
- Proactively investigate codebases for potential problems (bugs, concurrency issues, resource leaks, hot-path performance) rather than only fixing explicitly reported issues. The user expects autonomous, thorough sweeps that cover the complete subsystem, not just targeted fixes, and explicitly confirms they want every identified issue remediated ("corrija todos"). Confidence: 0.85
- When debugging, the user explicitly rejects adding debug/logging instrumentation as the primary fix ("eu n quero logs, quero que vc resolva") — prefer finding and fixing the root cause directly rather than adding logs to aid diagnosis. Confidence: 0.85
- For collections shared across Folia region/global threads: prefer `CopyOnWriteArrayList` for read-heavy lists mutated from another thread, `ConcurrentHashMap` for maps accessed across regions, and a lock+snapshot pattern (snapshot under lock, iterate the immutable copy outside the lock) when writes are frequent. Confidence: 0.65
- For path-following/racing-line lookups that previously did a full O(n) per-tick scan: bound the search to a small window (e.g. ±32 indices) around the last known index instead of scanning the whole list. Confidence: 0.70
- For any per-player operation dispatched from a global thread: use the region scheduler (`runTaskFor(plugin, player, …)`) before touching that player's location/entities — the global thread is not thread-safe for per-player access. Confidence: 0.65
- Use `DebugManager` for logging in hot paths and plugin lifecycle; never call `plugin.getLogger()` / `Bukkit.getLogger()` directly there (AGENTS.md rule). Confidence: 0.70
- Store infinite-repeating scheduler tasks in fields and cancel them in a `shutdown()` method wired into `onDisable`; also cancel spawned sub-tasks and clear static player-bound maps on disable and on player quit. Confidence: 0.65
- Before regenerating the JAR, validate edits with `mvn -o compile` (offline, fast when dependencies are cached) before running `mvn -o package`, so compile errors surface before the package step. Confidence: 0.60
- For entity AI/path-following movement: when overriding an entity's velocity each tick, blend the intended steer direction with the residual velocity (e.g. 85% path steer + 15% residual) instead of full-replacing it via `setVelocity(...)`, so collision knockback and other one-tick physics impulses are preserved rather than immediately clobbered. Confidence: 0.65
- For fixes that affect untested runtime physics/behavior (e.g. Minecraft entity collision physics), propose the fix with reasoning and ask the user for confirmation before applying/committing, rather than auto-applying — even when incremental fixing is otherwise preferred. Confidence: 0.65
- When starting work on a new Minecraft server version (e.g. 26.2), prefers cloning the project into a separate directory rather than modifying in-place, to keep version-specific changes isolated. Confidence: 0.60
- Prefers consolidating features as subcommands under an existing parent command (e.g. `/heat set ...`) rather than registering separate standalone command classes — a rejected "whole command" should be folded into the parent's subcommand tree, and the old command's registration and source file removed entirely. Confidence: 0.90
- Before committing in a fresh git clone, set per-repo `git config user.name` and `git config user.email` with GitHub noreply addresses (`...@users.noreply.github.com`), and run `git config --global --add safe.directory <path>` to resolve "dubious ownership" errors when the repo lives in a non-`$HOME` location. Confidence: 0.85
- When a Gradle project targets a Minecraft version requiring a non-default JDK (e.g. Java 25 for Folia 26.2), set `org.gradle.java.home` in `gradle.properties` to the specific JDK install path (e.g. `C:/Program Files/Java/jdk-25.0.4`) rather than relying on the system-default `java` — this is done together with bumping `JavaVersion` and `options.release` in `build.gradle`. Confidence: 0.80
- When upgrading Minecraft server versions, dependencies must be updated in a cascade: Paper API version, Java source/target level, and Lombok version are interdependent — an outdated Lombok (≤1.18.36) fails to load on Java 25, and `scoreboard-library-modern` was removed in newer Megavex releases (only `scoreboard-library-implementation` remains). Confidence: 0.75
- For Gradle-based Minecraft plugin projects (that ship with `build.gradle` + `gradlew`), the build/verify command on Windows is `gradlew.bat build` (run from the project root), not Maven — the agent always runs this before committing and checks `build/libs/` for the resulting JAR. Confidence: 0.80
